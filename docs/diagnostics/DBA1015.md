# DBA1015：Use Case 契約形狀無效

## 目的與預設嚴重性

`DBA1015` 將 Use Case 的公開操作收斂為可預期、傳輸層中立的
`ExecuteAsync` 契約。Roslyn Descriptor 的正式標題為
`Use Case contract shape is invalid`，分類為 `Architecture`。

| 欄位 | 值 |
|---|---|
| Diagnostic ID | `DBA1015` |
| 預設 severity | `Error`（`DiagnosticSeverity.Error`） |
| 預設啟用 | 是 |
| 產生位置 | 違規 Use Case 型別的宣告位置 |

## 適用範圍與觸發條件

此規則由 `UseCaseServiceProviderInjectionAnalyzer` 的 Named Type 分析執行，且不
分析產生的程式碼。

- 名稱以區分大小寫的 `UseCase` 結尾的 **介面**會檢查契約。
- 名稱以 `UseCase` 結尾的非抽象 **類別**會檢查實作。
- 名稱以 `UseCase` 結尾的抽象類別不會進入本規則的實作形狀檢查。

介面與非抽象類別都必須有恰好一個普通方法 `ExecuteAsync`。介面若找不到或找到
多個該方法，會立刻回報一次；非抽象類別也會回報一次。當剛好有一個
`ExecuteAsync` 時，該方法必須符合以下條件：

| 檢查面向 | 精確條件 |
|---|---|
| 回傳型別 | 必須是 `System.Threading.Tasks.Task` 或 `Task<T>`；`Task<T>` 的 `T` 不可為 `IActionResult`、`IResult`、名稱以 `Acknowledgement`／`Envelope` 結尾的型別，或命名空間以 `Microsoft.AspNetCore`／`Wolverine` 開頭的型別 |
| CancellationToken | 最後一個參數必須是非選擇性的 `System.Threading.CancellationToken` |
| 輸入數量 | `CancellationToken` 前最多一個輸入參數；超過一個時必須改為一個專用 Input 物件 |
| 輸入傳輸中立性 | 輸入型別名稱不可用 `Request`、`Command`、`Query`、`Message` 或 `Contract` 結尾，也不可實作簡單名稱為 `ICommand` 或 `IQuery` 的介面 |
| 輸入命名 | 單一非標量輸入型別必須以 `Input` 結尾；標量為 `bool`、`byte`、`sbyte`、`short`、`ushort`、`int`、`uint`、`long`、`ulong`、`float`、`double`、`decimal`、`char`、`string`，以及名稱為 `Guid`、`DateTime`、`DateTimeOffset`、`DateOnly` 或 `TimeOnly` 的型別 |

此外，介面與類別都不得宣告名稱為 `Handle` 或 `HandleAsync` 的方法。介面在
`ExecuteAsync` 數量不正確時會先結束該型別的後續形狀檢查；當
`CancellationToken` 不正確，該方法的輸入檢查也不會繼續進行。因此同一型別可以
因不同條件收到多個 `DBA1015`，也可能只收到較早執行的條件所產生的診斷。

## 違規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

public interface IActionResult { }

public interface IPlaceOrderUseCase
{
    // DBA1015：輸出為 HTTP 結果，不是傳輸層中立的輸出。
    Task<IActionResult> ExecuteAsync(CancellationToken cancellationToken);
}
```

下列契約同樣違規，因為沒有唯一的 `ExecuteAsync` 操作：

```csharp
using System.Threading;
using System.Threading.Tasks;

public interface IPlaceOrderUseCase
{
    Task HandleAsync(CancellationToken cancellationToken);
}
```

## 合規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

public sealed record PlaceOrderInput(string OrderId);
public sealed record PlaceOrderOutput(string OrderId);

public interface IPlaceOrderUseCase
{
    Task<PlaceOrderOutput> ExecuteAsync(
        PlaceOrderInput input,
        CancellationToken cancellationToken);
}

public sealed class PlaceOrderUseCase : IPlaceOrderUseCase
{
    public Task<PlaceOrderOutput> ExecuteAsync(
        PlaceOrderInput input,
        CancellationToken cancellationToken)
        => Task.FromResult(new PlaceOrderOutput(input.OrderId));
}
```

## 修正指引

1. 將 Use Case 的操作統一為唯一的 `ExecuteAsync`，移除或搬遷 `Handle`／
   `HandleAsync` 入口點。
2. 將最後一個參數改為非選擇性的 `CancellationToken`；不要提供 `= default`。
3. 將多個業務輸入封裝為單一 `*Input` 型別，並將 HTTP、Broker 或 CQRS
   Command／Query 訊息轉換留在傳輸／Handler 邊界。
4. 回傳 `Task` 或 `Task<TOutput>`；由 Controller 或 Handler 把 Use Case 輸出轉為
   `IActionResult`、訊息確認或框架 Envelope。
5. 對非標量輸入採用 `*Input` 後綴，並以符合規則的輸出型別取代傳輸層輸出。

## 已知限制與例外

- 判定使用型別的簡單名稱、命名空間前綴與少數特別型別，不驗證 DTO 成員、存取
  修飾詞、可空性、是否實作對應介面，或 Use Case 是否真的被呼叫。
- `Guid`、日期／時間型別的「標量」判定只看簡單名稱；同名的自訂型別也會被視為
  標量。相反地，名稱以 `Command` 等結尾的傳輸中立型別仍會被視為傳輸契約。
- 只禁止 `Task<T>` 的特定傳輸輸出；其他非 `Task` 回傳型別會先因不是 `Task` 或
  `Task<T>` 而違規。
- 類別不需要實作介面才會被檢查；抽象 `*UseCase` 類別則不檢查實作形狀。
- 規則不適用於只因名稱以 `Handler` 結尾的類別；Handler 邊界由 `DBA1017` 等
  規則處理。

## 設定與 Suppression

目前實作沒有自訂分析器選項。可用標準 `.editorconfig` 設定調整此診斷，例如：

```ini
[*.cs]
dotnet_diagnostic.DBA1015.severity = warning
```

對已審查且無法立即遷移的局部例外，可使用最小範圍的 pragma：

```csharp
#pragma warning disable DBA1015 // 暫時保留相容性的舊契約；已排定遷移。
Task<LegacyEnvelope> ExecuteAsync(CancellationToken cancellationToken);
#pragma warning restore DBA1015
```

請在 suppression 旁記錄例外原因與移除時機；不要以全域停用取代契約遷移。

- 實作：`src/Analyzers/ArchPrecept.Analyzers.Core/UseCaseServiceProviderInjectionAnalyzer.cs`
  的 `AnalyzeUseCaseContract`、`AnalyzeUseCaseImplementation`、
  `AnalyzeExecuteAsyncShape`、`IsTask`、`IsTransportContract` 與
  `IsTransportOutput`。
- Descriptor：`src/Analyzers/ArchPrecept.Analyzers.Core/RuleDescriptors.cs`
  的 `UseCaseContractShape`。
- 現有合規測試：
  `UseCaseServiceProviderInjectionAnalyzerTests.Allows_canonical_use_case_interface_and_implementation`。
- 現有違規測試：
  `Reports_http_result_as_use_case_output`、
  `Reports_optional_cancellation_token_on_use_case_contract`、
  `Reports_transport_command_as_use_case_input` 與
  `Reports_use_case_that_also_exposes_handler_entry`。

目前測試涵蓋代表性的輸出、CancellationToken、傳輸輸入與 Handler 入口；唯一
`ExecuteAsync`、多輸入與 `Input` 後綴等其餘分支仍應以目前實作的條件為準。
