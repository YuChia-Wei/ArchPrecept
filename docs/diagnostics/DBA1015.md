# DBA1015：Use Case 契約形狀無效

## 目的與預設嚴重性

`DBA1015` 將 Use Case 的公開操作收斂為可預期、傳輸層中立的
`ExecuteAsync` 契約。Roslyn Descriptor 的正式標題為
`Use Case contract shape is invalid`，分類為 `Architecture`。

| 欄位 | 值 |
|---|---|
| Diagnostic ID | `DBA1015` |
| 預設 severity | `Error`（`DiagnosticSeverity.Error`） |
| 預設啟用 | 是 |
| 產生位置 | 違規 Use Case 型別的宣告位置 |

## 設計理由與取捨

[傳輸中立應用邊界](../product/rule-design-rationale.md#application)支持把 Request、派送訊息與 Use Case 資料分開。產品進一步選定唯一 `ExecuteAsync`、專屬 `*Input`（保留無輸入／單一標準純量）、Task 結果及非選用 CancellationToken，以固定入口、資料責任及取消意圖。

代價是額外 Input 型別與轉換；這些名稱及 .NET 形狀是產品契約，並非架構作者指定語法。純 Application `CreateOrderCommand` 仍不符合非純量 Input 命名，但不因此自動成為 Transport。本候選按有效繼承／顯式實作與真正 BCL symbols 檢查，仍不證明執行時取消有被遵守。

## 適用範圍與觸發條件

檢查已辨識為 use-case 的介面及非抽象 class／record／struct。有效繼承／顯式實作的 ExecuteAsync 必須剛好一個，為 instance、非泛型且無 ref/out 參數，回傳真正 BCL Task／Task<T>，最後參數須為非選用 BCL CancellationToken。最多一個輸入；非純量輸入使用 Input 尾碼。Command／Query／Request 等名稱不是 transport 身分；不符 Input 形式時僅報形式錯誤。介面不暴露其他操作，實作不可暴露直接宣告、繼承或顯式介面的 Handle／HandleAsync（private helper 不屬入口）；輸入與 Task<T> 的 T 不可含已辨識 transport。這是選定的 `framework` 契約形狀。

0.0.3 起，角色由共用 `RoleClassifier` 辨識：明確 mapping → 內建／繼承契約 → 可選命名慣例。所有一般規則略過 generated code。目前未設定時採 `legacy`，以下名稱式範例以此預設為前提；選定 Profile 與規則適用性見 [設定與角色契約](../product/analyzer-policy.md) 與 [唯一 Catalog](../../rules/catalog.xml)。

## 違規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

using Microsoft.AspNetCore.Mvc;

public interface IPlaceOrderUseCase
{
    // DBA1015：輸出為 HTTP 結果，不是傳輸層中立的輸出。
    Task<IActionResult> ExecuteAsync(CancellationToken cancellationToken);
}
```

下列契約同樣違規，因為沒有唯一的 `ExecuteAsync` 操作：

```csharp
using System.Threading;
using System.Threading.Tasks;

public interface IPlaceOrderUseCase
{
    Task HandleAsync(CancellationToken cancellationToken);
}
```

## 合規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

public sealed record PlaceOrderInput(string OrderId);
public sealed record PlaceOrderOutput(string OrderId);

public interface IPlaceOrderUseCase
{
    Task<PlaceOrderOutput> ExecuteAsync(
        PlaceOrderInput input,
        CancellationToken cancellationToken);
}

public sealed class PlaceOrderUseCase : IPlaceOrderUseCase
{
    public Task<PlaceOrderOutput> ExecuteAsync(
        PlaceOrderInput input,
        CancellationToken cancellationToken)
        => Task.FromResult(new PlaceOrderOutput(input.OrderId));
}
```

## 修正指引

1. 將 Use Case 的操作統一為唯一的 `ExecuteAsync`，移除或搬遷 `Handle`／
   `HandleAsync` 入口點。
2. 將最後一個參數改為非選擇性的 `CancellationToken`；不要提供 `= default`。
3. 將多個業務輸入封裝為單一 `*Input` 型別，並將 HTTP、Broker 或 CQRS
   Command／Query 訊息轉換留在傳輸／Handler 邊界。
4. 回傳 `Task` 或 `Task<TOutput>`；由 Controller 或 Handler 把 Use Case 輸出轉為
   `IActionResult`、訊息確認或框架 Envelope。
5. 對非標量輸入採用 `*Input` 後綴，並以符合規則的輸出型別取代傳輸層輸出。

## 已知限制與例外

shape 支援有效介面繼承、泛型替換、class 繼承／override、public 同簽章 hiding 及顯式實作；同簽章 hiding 保留最衍生方法，不同 overload 仍分開計算。Guid／日期純量、Task 與 CancellationToken 必須是真正 BCL 定義。transport 使用明確 mapping 或真正平台組件／namespace；檢查陣列／泛型引數至八層，以及一層 public instance field/property（含繼承）。不追蹤任意深層物件、private storage、反射或 helper effect；超出此深度未分析，零診斷不是傳輸中立證明。ValueTask 不在已選 canonical 回傳形狀。

診斷 properties 記錄 ruleId、role、roleEvidence、confidence 與型別。命名慣例是低信心證據；零診斷不能當成完整架構合格。需要覆蓋證據時用 `Expected` 明確宣告範圍，未辨識／generated／停用分別由 DBA0002 回報；載入或設定失敗另處理。

## 設定與 Suppression

可用兩層 AdditionalFiles 設定 Profile、明確角色及單一規則 enabled／severity；設定格式與優先序見 [採用政策](../product/analyzer-policy.md)。標準 Roslyn severity 最後套用，但不會自行啟用被 Profile 排除的規則。

```ini
[*.cs]
dotnet_diagnostic.DBA1015.severity = error
```

可選 none／silent／suggestion／warning／error。暫時例外可使用最小範圍的 `#pragma warning disable DBA1015`／restore，並留下理由；不要以改名或整個 repository suppression 代替確認角色。
