# DBA1017：派送 Handler 必須轉接至一個 Use Case

## 目的與預設嚴重性

`DBA1017` 限制 Command／Query 派送 Handler 的相依邊界：它必須辨識到剛好一個
Use Case，且不可直接依賴 Repository 或 Domain Service。Roslyn Descriptor 的正式
標題為 `Dispatch Handler must adapt to one Use Case`，分類為 `Architecture`。

| 欄位 | 值 |
|---|---|
| Diagnostic ID | `DBA1017` |
| 預設 severity | `Error`（`DiagnosticSeverity.Error`） |
| 預設啟用 | 是 |
| 產生位置 | Handler 類別的宣告位置 |

## 適用範圍與觸發條件

此規則由 `UseCaseServiceProviderInjectionAnalyzer` 執行，且不分析產生的程式碼。它
只處理 C# 類別（不含介面），其簡單名稱以區分大小寫的 `CommandHandler` 或
`QueryHandler` 結尾；抽象 Handler 也沒有被此規則排除。

分析器把下列型別視為 Handler 的相依來源：所有 instance constructor parameter，
以及 `GetMembers()` 所取得每個方法的 parameter。接著依型別的顯示名稱去重後計數：

| 觸發 | 精確條件 |
|---|---|
| Use Case 數量不正確 | 來源中簡單名稱以 `UseCase` 結尾的不同型別數量不是剛好 `1` |
| 直接依賴 Repository／Domain Service | 任一來源的簡單名稱以 `Repository` 或 `DomainService` 結尾 |

兩個條件分別回報；例如沒有 Use Case 且又有 Repository parameter 時，同一個
Handler 會得到兩個 `DBA1017`。反之，建構函式中有一個 Use Case 與一個 Repository
時，Use Case 數量正確，仍會因 Repository 得到一個 `DBA1017`。

## 違規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

public interface IPlaceOrderUseCase
{
    Task ExecuteAsync(CancellationToken cancellationToken);
}

public interface IOrderRepository { }

public sealed class PlaceOrderCommandHandler
{
    // DBA1017：雖有一個 Use Case，仍不可直接依賴 Repository。
    public PlaceOrderCommandHandler(
        IPlaceOrderUseCase useCase,
        IOrderRepository repository) { }
}
```

## 合規範例

```csharp
using System.Threading;
using System.Threading.Tasks;

public interface IPlaceOrderUseCase
{
    Task ExecuteAsync(CancellationToken cancellationToken);
}

public sealed class PlaceOrderCommandHandler
{
    public PlaceOrderCommandHandler(IPlaceOrderUseCase useCase) { }
}
```

## 修正指引

1. 將 Handler 調整為恰好辨識一個 `*UseCase` 相依，並將 Command／Query 的輸入
   轉為該 Use Case 所需的輸入。
2. 移除 Handler 直接注入的 `*Repository` 與 `*DomainService`；將資料與領域工作
   放入 Use Case 及其下游協作者。
3. 若一個 Handler 同時協調多個 Use Case，將協調責任移至一個明確的上層 Use Case
   或重新拆分派送邊界。
4. 修正後確認不只存在一個欄位，而是 constructor／方法 parameter 來源中剛好有
   一個不同的 `*UseCase` 型別。

## 已知限制與例外

- 分類完全依賴類別與型別的簡單名稱；規則不驗證 Handler 是否真的呼叫 Use Case、
  是否處理 `ICommand`／`IQuery`，或 Use Case 是否為有效契約。
- 只有名稱以 `CommandHandler` 或 `QueryHandler` 結尾的類別會觸發此規則；其他
  `*Handler`、介面與產生的程式碼不在範圍內。
- Use Case 計數只看 constructor 與方法 parameter，不看欄位、屬性、方法主體、
  DI 註冊或執行期解析。僅把 Use Case 存在欄位中而沒有對應 parameter，仍會被視為
  零個 Use Case。
- 規則只禁止名稱以 `Repository`／`DomainService` 結尾的相依；它不要求 Handler
  除了一個 Use Case 外完全沒有其他型別的 parameter。
- 即使類別是 `abstract`，只要名稱符合 `CommandHandler`／`QueryHandler` 仍會被檢查。

## 設定與 Suppression

目前實作沒有自訂分析器設定。可用 `.editorconfig` 調整標準 Roslyn 診斷嚴重性：

```ini
[*.cs]
dotnet_diagnostic.DBA1017.severity = warning
```

對經核准且短期存在的轉接層，使用局部 suppression 並保留理由：

```csharp
#pragma warning disable DBA1017 // 過渡 Handler；Repository 已排入移至 Use Case 的工作。
public PlaceOrderCommandHandler(
    IPlaceOrderUseCase useCase,
    LegacyOrderRepository repository) { }
#pragma warning restore DBA1017
```

不要透過全域 suppression 掩蓋 Handler 的長期資料或領域相依。

## 對應實作與測試

- 實作：`src/Analyzers/EngineeringGuardrails.Analyzers.Core/UseCaseServiceProviderInjectionAnalyzer.cs`
  的 `AnalyzeDispatchHandler`、`IsDispatchHandler`、`IsUseCaseType` 與
  `IsForbiddenHandlerDependency`。
- Descriptor：`src/Analyzers/EngineeringGuardrails.Analyzers.Core/RuleDescriptors.cs`
  的 `DispatchHandlerBoundary`。
- 現有合規測試：
  `UseCaseServiceProviderInjectionAnalyzerTests.Allows_command_handler_that_adapts_to_one_use_case`。
- 現有違規測試：
  `UseCaseServiceProviderInjectionAnalyzerTests.Reports_command_handler_with_repository_dependency`。

目前測試覆蓋「一個 Use Case」合規情況與「一個 Use Case 加 Repository」違規情況；
零個／多個 Use Case、方法 parameter 與 `DomainService` 分支尚無專屬測試，精確行為
以實作條件為準。
