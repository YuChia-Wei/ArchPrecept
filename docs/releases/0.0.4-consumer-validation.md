# 0.0.4-preview：實際 consumer 試用

日期：2026-11-02。套件來源為 GitHub Packages，對應[發布紀錄](0.0.4-preview.md)的實際發布成品。兩個專案各在 F: RAMDISK 的隔離 Git worktree 驗證，未將試用變更合併至 consumer 原分支。

## 結果

| Consumer／基線 | 試用 | 結果 |
|---|---|---|
| dotnet-webapi-lab `8bc05b8` | 既有 Analyzer、Domain、Application 三套件由 0.0.3-preview 升級 | solution build 通過；既有 34 個測試為 27 passed、7 failed。相同來源切回 0.0.3-preview 後 34 passed |
| dotnet-distributed-architecture-lab `7a0bff4`（本機既有名稱 dotnet-mq-arch-lab） | 原本沒有 ArchPrecept 套件；以 analyzer-only、明確自有契約 mapping 試用 | baseline build 通過；有效試用設定下出現 11 個 DBA1001 errors，採用驗收未通過 |

這些結果證明發布成品可載入及實際規則／契約影響，不是兩個 consumer 已完成採用。沒有全面 suppression、修改 consumer 業務程式或放寬產品規則來使檢查通過。

## Web API：identity 生命週期差異

只調整四個專案／targets 檔中的三套件版本。還原 cache 的三個 nupkg SHA-256 與實際 main 發布 run artifact 相同，來源 metadata 為 GitHub feed。SDK 為 10.0.403；build 為零警告／錯誤，未發現 Analyzer 載入失敗。

受影響路徑為 `SimpleDocumentEntity.AssignIdentity`、`MockDataRepository.SaveAsync` 及測試 repository：以 `Id == 0` 或 `Id != 0` 判斷尚未持久化，但建構時沒有先指派 Id。0.0.4-preview 的 getter 依本版契約擲出 `InvalidOperationException: Entity identity has not been assigned.`。同樣的模式亦存在實際 `SimpleDocumentRepository.SaveAsync`，這是來源檢查，未執行真實資料庫驗收。

使用同一組既有 Domain／UseCase／HTTP 測試、相同 SDK 與建置模式，只將套件切回 0.0.3-preview，結果從 7 failed 變為 34 passed，支持此契約改變造成升級失敗。測試後 worktree 恢復 0.0.4-preview 引用，保留失敗供後續處理。

後續須明確選擇 consumer 的 identity 生命週期：若沿用既有 0 sentinel，應明確初始化該值，例如在適用建構路徑呼叫 `base(0)`；或改以獨立狀態判斷是否已取得儲存 identity。兩者都應保留「已持久化 identity 不可任意變更」的既有領域規則。本輪只提出處置方向，未修改 consumer 行為，也未把讀取前初始化要求回退。

環境限制：第一次使用缺少 package scope 的 CLI credential 失敗；改沿用既有 NuGet credentials 後成功。發布後曾命中舊 HTTP 索引，使用新的 F: HTTP cache／no-http-cache 後取得 0.0.4-preview。Windows AppHost 建置曾遇 DLL 鎖定；兩版本對照均採 `UseAppHost=false`、`UseSharedCompilation=false`、單一 MSBuild node 的 managed DLL 模式，不代表原生 AppHost 已驗收。

## MQ：自有契約與 repository 能力差異

只新增 analyzer 套件、AdditionalFiles、NuGet source mapping 及 SARIF 輸出設定。未安裝 ArchPrecept runtime contracts。試用選擇 core、web-api、messaging、event-sourcing、framework、ddd，保留其原本 severity 與命名慣例，並將共用 Entity／Aggregate／ValueObject／ES 與 Repository／Query／DomainEventDispatcher 映射到實際 `Lab.BuildingBlocks.*` 型別。

設定按實際參考範圍區分 Domain 與 Application：Products／Orders／Inventory 的 Domain，以及四個業務 context 的 Application／Infrastructure／WebAPI 是本次目標。Procurement.Domain 不參考共用 Domain 契約，未套用該組 mapping；shared contracts、外部 sandbox、其他 lab 範例與測試專案不宣稱被完整評估。第一次將 mapping 套到無對應參考的專案而產生 DBA0001，已修正試用設定，最終結果不含這類配置錯誤。

| 位置 | 最終 DBA1001 |
|---|---|
| InventoryItemDomainRepository | FindByIdsAsync、SaveAllAsync、DeleteAsync 超出 aggregate port 的公開能力限制：3 項 |
| ProductDomainRepository | 同上：3 項 |
| OrderEventSourcingRepository | 公開 CommitAsync：1 項 |
| PostgresPurchaseStore | 混合 query／write／commit ports；CreateOrGetAsync 暴露寫入，FindByIdAsync／ApplyOutcomeAsync／MarkUnknownAsync 回傳 domain aggregate：4 項 |

前七項可直接對照目前 DBA1001 的額外公開能力政策。Procurement 的四項涉及同一 adapter 實作多個讀寫 port，應進一步核對 consumer 的實際依賴視圖與產品 query-only 政策，不能僅憑診斷將其標為 consumer 缺陷或 Analyzer 誤報。本輪不自行拆分 adapter 或修改既有交易邊界。

SDK 10.0.403 的 baseline solution build 為 15 warnings／0 errors；最終試用為 8 warnings／11 errors。錯誤阻止部分下游專案編譯，不能把較少 warnings 視為改善，也不能宣稱未到達的 Controller 或 runtime 路徑通過。xUnit v3 要求 AppHost，baseline 使用專案預設 AppHost 成功；沒有沿用 Web API 的關閉 AppHost 參數。試用 build 未通過，因此未執行 MQ 的升級後 runtime tests 或外部 broker／資料庫驗收。

## 下一階段

正式版前先完成 Web API identity 採用決策，以及 MQ 額外公開能力／多 port adapter 的逐項判讀。再依實際修改重跑受影響的既有測試；不因本報告或版本規劃更新重跑全套矩陣。不能將發布 CI 成功替代上述採用結果，也不覆寫既有 0.0.4-preview bytes。

後續分別由 [#18：Web API identity 採用](https://github.com/YuChia-Wei/ArchPrecept/issues/18)及 [#19：MQ Repository／多 port 判讀](https://github.com/YuChia-Wei/ArchPrecept/issues/19)追蹤。兩項均保存問題、待決方案與驗收條件；建立工作項目不表示採用已修復。
