# 版本與支援政策

ArchPrecept 的七個套件使用相同版號，可各自安裝。首個無預發行後綴的公開版本為 `0.1.0`。維護與相容承諾自首個穩定版發布起生效。

## 平台與支援範圍

| 面向 | 支援基線 |
|---|---|
| Consumer SDK | .NET SDK 8 與 10 |
| Contracts | `net8.0` |
| Analyzer | `netstandard2.0`、Roslyn 4.8。Analyzer 在編譯器內執行，載入相容性取決於 SDK 或 IDE 內的 Roslyn。 |

套件安裝驗收檢查 SDK 8 與 10 的還原、建置及預期 Diagnostic。API 的跨框架行為和個別 IDE 版本的相容性另依各自驗證範圍。產品建置使用的 SDK 與 consumer 支援版本分別管理。

## 預覽與候選版

首個無預發行後綴的公開版本之前，預發行版本之間沒有向後相容保證。公開 API、Diagnostic／Rule ID、設定 schema、預設值與套件邊界可直接演進，採用端依當版契約調整。每版的 Rule／Diagnostic ID 須唯一，文件、設定、實作與測試須一致。版本說明須交代新版用法及受影響的契約。

安裝預發行套件時指定包含後綴的完整版號。

| 版號 | 用途 |
|---|---|
| `x.y.z-preview.N` | 公開尚在演進的功能與契約。同一版本基線的新成品遞增 `N`。 |
| `x.y.z-rc.N` | 為已凍結的候選契約提供外部驗證。首個 RC 使用 `rc.1`，修正後遞增尾碼。契約或範圍重新開放時回到 Preview。 |
| `x.y.z` | 無預發行後綴的正式成品。首個正式版可由已驗收的 Preview 或 RC 準備，並以實際要發布的版號與成品完成正式版條件。 |

七包的發布版號由 `v<PackageVersion>` tag 取得。每個已發布的套件 ID 與版本對應固定成品，禁止覆寫。

## 合併與升版判準

先確認要交付的內容及實際封裝輸入，再決定是否升版。整合來源、更新網站與交付套件各自判斷。根目錄 `README.md` 等文件會隨包交付，修改也可能改變封裝內容。

| 交付情境 | 升版要求 |
|---|---|
| 只更新 repository 文件、規則理由或開發規範 | 沿用既有套件版本，檢查受影響的文件。 |
| 修正官網安裝說明、診斷範例或導覽 | 沿用文件描述的套件版本，更新網站內容。 |
| 將新版 README、API XML、其他隨包內容或套件 metadata 交付至套件來源 | 選用尚未發布的新版本。 |
| 交付 Analyzer 判定、Diagnostic、Catalog／schema、公開契約、套件相依或其他產品行為的變更 | 選用尚未發布的新版本，驗證受影響的行為與套件，清楚說明本版能力及限制。 |
| 重新建置或驗證既有版本 | 沿用原版號辨識受驗證範圍。重建成品須與原發布成品區分。 |
| 發布首個無預發行後綴的公開版本 | 完成下列首版條件，驗證正式版發布機制與實際成品。 |

更新公開安裝說明中的平台可用狀態前，先完成該平台的 consumer 驗收。成熟度以該版交付範圍與驗收條件判定。

## 首個正式版條件

`0.1.0` 的交付條件包括七個套件、完整的規則與公開 API 文件、NuGet.org 匿名安裝及固定版號的官網手冊。

## 穩定版相容與維護

只維護最新穩定線。下一條穩定線發布時，前一條結束一般修補。`0.x` 的 patch 版保持同一穩定線的相容性，例如 `0.1.1` 相容於 `0.1.0`。破壞性變更使用下一條 `0.y.0`。自 `1.0.0` 起採用 SemVer，major 表示不相容變更，minor 表示相容擴充，patch 表示相容修正。

相容審查涵蓋公開 API、相依套件與最低平台、Diagnostic ID 與判定語意、預設 Profile 與 severity、設定 schema、公開報告欄位，以及文件列出的範本命令與參數。新增預設診斷、提高 severity 或修正漏判若會使既有受支援建置失敗，須使用新的不相容版本線並提供更新說明。新增 opt-in 規則與修正誤報仍須評估既有設定和 warnings-as-errors 的影響。
