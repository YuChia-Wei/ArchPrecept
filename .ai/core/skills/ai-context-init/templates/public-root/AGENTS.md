# AGENTS.md

This is the canonical English collaboration guide for AI agents and humans in
this repository. Keep repository-specific facts concise and backed by current
repository evidence. Respect any explicitly selected target language ownership.

## Scope And Precedence

- Follow user instructions and explicit approvals before repository guidance.
- A deeper AGENTS file takes precedence for its subtree within higher-level authority.
- Do not invent project truth, authorization, execution or validation. State
  material assumptions, conflicts and unresolved decisions.
- Make the smallest coherent change that satisfies accepted scope and observable
  completion criteria. Preserve unrelated changes and custom content.

## Progressive Context Loading

1. Start with the request, current Git/worktree state when available, this file and
   explicitly named artifacts.
2. When a skill applies and is available, select one owning route from the actual
   target runtime entries. Load only its entry and applicable references. Reload
   full source only for metadata, maintenance or discrepancy resolution.
3. Expand context only for the current task, phase or finding. Follow existing
   target workflow policy when applicable; a missing policy is not an invented gate.
4. Use the verified project index for navigation when needed. Load README,
   architecture, configuration and detailed rules only when relevant.
5. Keep project-specific facts outside reusable framework assets and verify
   material conclusions against current source and accepted project decisions.

## Execution And Validation

- Touch only required files and follow the target's branch/workflow rules.
- Continue reversible implementation and repair within authorized scope. Reuse
  existing approvals; ask for missing authority or material owner decisions.
- Implementation, push, PR, merge, Issue/Project updates, tags, release and
  publication are separate states unless authorized together.
- Resolve target commands, working directories and prerequisites before execution.
  Run required gates and the narrowest meaningful checks; broaden or repeat only
  for new changes, failures or unresolved concerns.
- Report failed, skipped, blocked and unrun checks truthfully. A discovered
  command or successful document parse is not evidence of product execution.
- Follow an existing target commit policy before committing. Do not manufacture
  policy paths, required services or approval records.
- Delegate only when authorized and available. Bound the task, ownership and
  evidence; retain one tracked writer per worktree and report actual invocations.
- Select the least costly sufficient model and supported effort for each delegated
  task using the target's adopted policy; prefer deterministic tools for mechanical
  work. Specify the choice explicitly rather than inheriting the parent model.
  Missing policy, unavailable choices or conflicting runtime overrides stop the
  affected delegation. Confirm actual invocation identity separately from configuration.
- Keep model preferences and custom agent instructions project-owned and separate
  from managed framework resources. Updates preserve local choices and unknown
  entries; compare baseline/local/candidate before adopting a changed default.
  When the project selects sub-agent resource management, author custom packages
  under `.ai/project/sub-agents/` and use its `.ai/project/sub-agent-registry.json`
  for provenance and explicit role routes. Check the chosen package and runtime
  entry before delegation. Capability overlap proposes a comparison; it does not
  switch a route, confer installer ownership or prove runtime activation.
  A role name or available model grants no spending permission. Reuse approved
  choices; escalation beyond the accepted model/effort boundary needs explicit authority.

## Mandatory public requirement boundary

For public Epic, Feature, User Story and Issue/ticket descriptions and comments,
MUST describe the product need independently: problem, beneficiary or outcome,
scope, relevant scenarios, observable acceptance and real dependencies. Readers
must not need a private conversation to reconstruct the requirement.

The same boundary applies to public PR descriptions, comments and review
discussions. Describe the concrete problem, resulting behavior, scope, validation
and defect-review evidence, limitations and related requirements. PRs are part of
the public Issue channel, not a workflow exception.

MUST NOT publish execution authorization or its approval/revision history, agent handoff,
resume instructions or execution checkpoints in these public channels. Record
and retrieve authorization and handoff through the target's workflow mechanism.
An Issue system is not a substitute workflow store. If that mechanism is unavailable,
report the missing record or blocked handoff; do not silently fall back to an Issue,
PR, comment, or another store, and do not claim a transfer occurred.

Feature inventories, requirement/design discussion, product decisions and supported
requirement revisions/status, linked
Issues, and concise completed/pending/deferred feature summaries MAY remain.
Explain dependencies such as "requires #123's API" and link relevant result evidence
without copying execution logs. Product approval/permission behavior is valid
requirement content; permission for an agent to push or merge is execution authority.
Classify by purpose and meaning, not forbidden words or headings.

Preserve technical verification results, supported findings and coverage limits;
keep agent assignments, approval history and continuation or integration
instructions in the workflow. A template does not authorize copying those
execution records into public prose.

Before creating or updating content, check this boundary and correct violations
within the authorized scope. In a read-only review, report the selected violation
and a bounded correction; do not edit it. Keep valid requirements, IDs, decisions,
uncertainty and acceptance meaning. Do not mandate one wording, heading order,
provider, Workflow Board deployment or new storage product. Unselected historical
records remain unchanged. Drafting or reviewing requirements never grants execution
permission or proves implementation, adoption or acceptance.
